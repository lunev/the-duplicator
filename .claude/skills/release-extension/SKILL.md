Release flow for The Duplicator (Chrome MV3 extension):

1. Read the `version` field in `app/public/manifest.json` — this is the source of truth for the release version. If the user asked to bump the version (e.g. "release 7.0.5"), update `app/public/manifest.json`'s `version` first.
2. Update `app/package.json`'s `version` field to match `app/public/manifest.json`'s `version` exactly. These two fields are maintained independently in this repo and must be kept in sync manually.
3. Figure out what changed: find the previous release commit with `git log --oneline -- app/public/manifest.json` (each release is a version-bump commit), then review the commits/diff since then.
4. Add a new entry under README.md's `## Changelog` section for this version, covering **only user-visible changes that are worth telling a user about**: new features, redesigned UI, changed behavior/interactions. Leave out anything with no visible effect (dependency/framework upgrades, refactors, internal validation logic, build tooling, tests, lint, CI, dev-only scripts, etc.) *and* anything that's technically visible but too minor to be worth a changelog line — small styling tweaks like a button becoming round instead of square, a color adjustment on one element, spacing nudges. The bar isn't "did this change pixels," it's "would a user actually care enough to read a line about it." When in doubt, leave it out rather than padding the list. This section is the permanent historical record across all releases — always append a new `### <version> - <date>` entry above the previous ones, never overwrite past entries. If a release has no changelog-worthy changes, add an entry saying so (e.g. "Internal changes only") rather than skipping it or padding it with minor/internal work.
5. Sync `app/src/constants/changelog.ts`'s `CHANGELOG` constant to match the new README.md entry — set `version` to the new version and `features` (a `{title, description}[]`; short title) to the same user-visible items just added to the changelog. This constant only ever holds the *latest* release's notes — it's what `UpdateInfo.tsx` shows as a dismissible "What's New" banner after a user's extension auto-updates (flag set by `chrome.runtime.onInstalled` in `service-worker.ts`), rendered inside the extension's popup, which has **limited height** — the banner must stay small, it can't push the actual parameter list out of view or force scrolling. Keep this tight: prefer 1–3 features max per release (pick the most important if more changed — README.md can hold the full list, this banner doesn't have to), and keep each `description` to one short, concrete sentence — specific enough that the user understands what changed (not a vague "various improvements"), but no longer than it needs to be. Specific-and-brief, not vague-and-short or thorough-and-long. If the changelog entry was "no user-visible changes," leave `CHANGELOG` as it was from the last release that had real changes, so the banner never shows an empty/pointless update.
6. Run `npm run build` from inside `app/`. This runs `tsc -b` (typecheck), a production `vite build`, then `build-zip.js`, which zips the `app/build/` output into `chrome-webstore/releases/<name>-v<version>.zip` using the version from `app/public/manifest.json`.
7. Confirm the new zip exists at `chrome-webstore/releases/the-duplicator-v<version>.zip` (or the equivalent sanitized name `build-zip.js` produces) and report the path back to the user.
8. The resulting zip (plus the version, `README.md`, and `app/src/constants/changelog.ts` changes) is meant to be committed to git (release zips under `chrome-webstore/releases/` are tracked in this repo) — stage and mention it, but don't commit or push without the user's explicit go-ahead.
